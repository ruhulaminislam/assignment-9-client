# 01. Project Overview

## 1.1 Project Description

SalonBook is a salon appointment booking platform where customers can explore salon services, view service information, and request appointments online.

The salon administrator can create and manage salon services, review appointment requests, confirm or cancel appointments, manage customers, and monitor payments.

Customers can manage their own appointment requests and pay for confirmed appointments through Stripe.

## 1.2 Project Objective

Build a beginner-friendly, role-based web application using:

- Next.js
- TypeScript
- Express.js
- MongoDB
- Better Auth
- JWT Authentication and Authorization
- REST APIs
- Stripe

## 1.3 System Users

The platform has two primary roles:

**Customer**
- Explore salon services.
- Request appointments.
- Manage personal appointments.
- Pay for confirmed appointments.
- View appointment and payment history.

**Admin**
- Manage salon services.
- Manage appointment requests.
- Manage registered customers.
- Monitor transactions.
- Access the Admin Dashboard.

# 09. Payment System

Customers can pay for confirmed salon appointments through Stripe.

## 9.1 Payment Flow

1. Customer submits an appointment request.
2. The appointment is saved with `pending` status and `unpaid` payment status.
3. Admin reviews and confirms the appointment.
4. Customer opens the Customer Dashboard.
5. Customer navigates to My Appointments and clicks Pay Now.
6. Customer is redirected to Stripe Checkout.
7. After successful payment, Stripe redirects the customer to the Payment Success page.
8. If payment is cancelled, Stripe redirects the customer to the Payment Cancel page.
9. A verified Stripe webhook updates payment status to `paid` and saves the transaction.

## 9.2 Payment Success Page

After successful payment:

- Show payment confirmation.
- Save the transaction.
- Update payment status only after verified payment confirmation.

**Database:** `transactions` Collection

## 9.3 Payment Security

- Use Stripe Checkout.
- Verify Stripe webhook events.
- Payment status must only be updated after a verified webhook event.
- Never trust the frontend success redirect as proof of payment.
- Admin must not manually mark an unsuccessful payment as successful.

# 14. Database Architecture

Use MongoDB.

Better Auth manages its own authentication-related collections.

Use the following four main collections and proper references between collections. Do not create unnecessary collections for the same information.

## 14.1 Users Collection

**Managed by:** Better Auth

Fields:

- `name`
- `email`
- `image`
- `role`
- `isBlocked`

## 14.2 Services Collection

Fields:

- `serviceName`
- `category`
- `description`
- `price`
- `duration`
- `image`
- `status` (`active` or `inactive`)
- `createdAt`

## 14.3 Appointments Collection

Fields:

- `serviceId`
- `customerId`
- `appointmentDate`
- `timeSlot`
- `message`
- `servicePrice`
- `paymentStatus` (`unpaid` or `paid`)
- `status` (`pending`, `confirmed`, or `cancelled`)
- `createdAt`

## 14.4 Transactions Collection

Fields:

- `appointmentId`
- `customerId`
- `amount`
- `currency`
- `stripeSessionId`
- `status` (`paid` or `failed`)
- `createdAt`

Maintain proper references between collections.

Do not create duplicate collections for information already managed by Better Auth.
